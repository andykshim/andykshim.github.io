![Ul3422 Card](/assets/ul3422/card.avif)

Every High Frequency Trading strategy fundamentally requires being first in line. Tick-to-trade latency is the most important metric of networking hardware in
this application, and it represents the time it takes to receive new market information from the exchange, and execute a new trade order based on the information.

The Alveo UL3422, along with the 4-port sister UL3524, are AMD's flagship cards for ultra-low latency trading. It combines the Virtex UltraScale+ XCVU2P FPGA 
with new GTF transceivers to achieve trading in nanoseconds. The UL3524 currently holds the record of 13.9 ns on the STAC-T0 benchmark measuring tick-to-trade latency [source](https://docs.stacresearch.com/news/AMD240422).

This project brings up the AMD Alveo UL3422 ultra-low latency FPGA card for 10G Ethernet, starting from bare JTAG connectivity and ending with a live link to a Solarflare NIC. This card combines the UltraScale+ XCVU2P FPGA with new GTF transceivers to achieve trading in nanoseconds. Its 4-port sister, the UL3524 currently holds the [record](https://www.amd.com/en/blogs/2024/amd-sets-stac-benchmark-world-record-for-fastest-e.html) of 13.9 ns on the STAC-T0 benchmark measuring tick-to-trade latency.

The UL3422 is heavily NDA-protected with little out-of-the-box support. Many reference designs are missing compared to the UL3524, and the few examples provided are copy-pasted with omissions — often containing errors in the documentation, or source code, or both.

We spent the first month establishing basic connectivity — wrong cable drivers, missing device files, getting `hw_server` running on hft11 — and validated the JTAG path with a binary-counter test image. From there we ported AMD's UL3524 reference designs to the UL3422, rewriting them into non-project Tcl + Make flows that build end-to-end on hft06 with no GUI.

**What we built and verified:**
- **QSFP-DD I2C** — Brought up QSFP-DD power and talked to optical module management interfaces
- **Renesas jitter cleaner** — Programmed the RC38612 via the BRAM-based I2C sequencer, added a fabric frequency counter to verify all four OTP clock configs, built an interactive I2C path for register-level access, and discovered/fixed a byte-order bug in AMD's `txt_to_mem.pl` script
- **Near-end PMA loopback** — Bit-perfect TX→RX loopback at 10G as a GTF-level sanity check
- **RECOV_CLK** — Ported the recovered-clock design (remapped GTF tiles, swapped state machines for single-JC / 2-port layout, corrected AMD's documentation where it disagreed with RTL)
- **ILA Ethernet** — Card-to-card 10G Ethernet with packet replay, verified TX/RX against the Solarflare NIC in hft11
- **Fused PCS+MAC** — Custom 2-stage 10GBASE-R datapath bypassing the elastic buffer, with Python-generated LFSR equations

## Prerequisites & Environment Setup

**Before you start, make sure the following are in order:**

1. **UL3422 Secure Site Access** — Request access through Prof. Lariviere's AMD contact. The UL3422 is NDA protected; device files and certain reference designs are not publicly available. You need access to *some (intentionally undiscolsed here)* datasheets, as well as the XCVU2P-3FSVJ2104E license for Vivado.

2. **Vivado GUI access** — Request access to `001FpgaDevGuiDesktop`. This is the only way to use the Vivado GUI. Everything is doable via command line, but to varying degrees of efficiency. Most of the project is ready to be called directly from command line while you wait on this. 

3. **Board visibility** — Run `lspci` on hft11 to confirm the UL3422 is detected. If not, check cable drivers and JTAG connectivity.

4. **Perl** — Required for `txt_to_mem.pl` (Renesas I2C flow). Not installed natively on the Windows machines; available via Git Bash (`C:\Program Files\Git\usr\bin\perl.exe`).

**A note on Vivado versions:** At the time of this report we run 2024.1 locally due to Apple Silicon compatibility issues. The hft servers have 2024.2 installed. This shouldn't cause any critical issues — we certainly didn't encounter any — but some script paths or version checks may need minor edits to run cleanly. These are noted on a case-by-case basis in each subsection.

5. **tmux for hw_server** — Consider running `hw_server` inside a tmux session on hft11. This lets multiple people connect to the board without restarting the server.

## Hardware Setup

The hardware configuration varies by test. The key things to know:

**Port numbering:** TOP is QSFP-DD Port 1, BOTTOM is QSFP-DD Port 2. ([UL3422 datasheet](https://docs.amd.com/r/en-US/ds1016-ul3422/Card-Interfaces))
![QSFP Port Labels](./assets/ul3422/qsfp_ports.jpg)

**Cables and modules:**
- The UL3422 has two QSFP-DD ports, each capable of 10G/25G networking. QSFP-DD is a high-density form factor; the Solarflare NIC in hft11 uses SFP+, a single-lane 10G form factor.
- We have a **QSFP-DD to SFP+ DAC** (direct-attach copper) cable for connecting the UL3422 to external networking cards.
- We also have a **QSFP28 passive loopback module** for TX-to-RX loopback testing without an external link partner.

<img src="/assets/ul3422/loopback_module.jpg" alt="Loopback Module" width="400">

**ILA Ethernet configuration** (card-to-card): This is the only example that does live Ethernet with an external NIC. Port 1 of the UL3422 connects via the DAC cable to the Solarflare NIC in hft11.

<img src="/assets/ul3422/wire_setup.jpg" alt="UL3422 and Solarflare X2522 Setup" width="400">

**Note on external power:** The UL3422 does not require external 8-pin PCIe auxiliary power. However, without it, QSFP module power is limited to 3.5 W ([UL3422 datasheet](https://docs.amd.com/r/en-US/ds1016-ul3422/PCIe-AUX-Power)). Per the [QSFP-DD spec](http://www.qsfp-dd.com/wp-content/uploads/2024/07/QSFP-DD-Hardware-Rev7.1.pdf), this restricts modules to Low Power Mode (below Power Class 2).

## Known Issues & AMD Errata

- **`txt_to_mem.pl` reversed byte order** — AMD's Perl script extracts multi-byte data fields right-to-left (LSB first), producing incorrect I2C wire order for the RC38612 page register. The bug is masked because the example programs config 15 (the power-on default). See [Renesas Jitter Cleaner](#renesas-jitter-cleaner) for details and fix.
- **RECOV_CLK MAC/RAW bank labels swapped** — The original RECOV_CLK README and block diagram have the MAC and RAW GT bank assignments reversed. Always verify against `clk_recov.v`, not the docs.
- **XDC pin function typos** — Several XDC comments label RX pins as TX and vice versa. Cross-reference against the package CSV or RTL.
- **QSFP I2C state machine cannot recover** — If an invalid I2C address is issued, the state machine stalls. There is no software reset — you must reload the bitstream.

## QSFP I2C

### Architecture

Automated power-up and I2C management for the UL3422's two QSFP-DD modules:

```
JTAG-AXI ──AXI-Lite──► reg_qsfp_i2c_logic ──► AXI IIC (axi_iic_0)
                              │                       │
                        state_machine_top              │
                         ├── state_machine_pwr         ├──► PCA9546 I2C MUX (0xE0)
                         └── state_machine_sb          │      ├── QSFP SB Expander (0x40)
                                                       │      └── QSFP Module I2C (0xA0)
                                                       └──► Power IO Expander (0x42)
```

Other diagrams are available [here](https://xilinx.github.io/Alveo-Cards/cards/ul3422/build/html/docs/QSFP_I2C/README.html).

### Description

The QSFP I2C design provides automated power sequencing and I2C access for both QSFP-DD modules. Three state machines handle the bring-up: `state_machine_top` orchestrates the sequence, `state_machine_pwr` manages power rail enable/disable via the I2C power expander, and `state_machine_sb` controls per-port sideband signals (reset, low-power mode, module select) through the I2C MUX.

After power-up, the QSFP module's management interface (SFF-8636) is accessible at address `0xA0` through the I2C MUX. This allows reading transceiver telemetry (temperature, voltage, optical power) and module identification (vendor, part number, serial).

**I2C device map (8-bit addressing):**

| Address | Device | Purpose |
|---------|--------|---------|
| `0x42` | Power IO Expander | Enable/disable QSFP power planes |
| `0xE0` | PCA9546 I2C MUX | Route I2C to QSFP 0/1 sideband or module I2C |
| `0x40` | QSFP SB Expander | LPMODE, MODSELL, RESETL, interrupt, present |
| `0xA0` | QSFP Module | Transceiver management (SFF-8636) |

**Note:** The AMD documentation frequently lists both 8-bit and 7-bit addresses (last bit R/W flag) for I2C devices. Be careful not to mix these up.

### Build & Run

```bash
cd tests/qsfp_i2c
make all    # Synthesize in non-project mode → build/qsfp_i2c_top.bit
```

After programming the device, in the Vivado Tcl console:

```tcl
source scripts/qsfp.tcl       ;# Load low-level I2C helpers (reg_wr, reg_rd, i2c_wr, i2c_rd)
source scripts/qsfp_test.tcl   ;# Load high-level test wrappers

# Step 1: Power up QSFP modules
qsfp_enable_power_only

# Step 2: Reset and bring up sideband for each port
qsfp_reset_port 0
qsfp_reset_port 1

# Step 3: Access module I2C (read transceiver identifier)
qsfp_access_i2c 0

# Optional: dump register space
dump_i2c_regs 0xA0 0x00 16
```

### Test Procedure & Results

1. Run `qsfp_enable_power_only` — should complete without errors
2. Run `qsfp_reset_port 0` — should print sideband status (MODPRSTL indicates module present)
3. Run `qsfp_access_i2c 0` — should return a valid identifier byte from `0xA0` register `0x00`
4. For full telemetry: write page select register (`0x7F`) then read temperature, voltage, and optical power registers per SFF-8636

### Design Notes

- **8-bit I2C addressing.** The Tcl scripts use 8-bit addresses (R/W bit at LSB). The hardware handles 8-bit to 7-bit conversion internally.
- **Port indexing.** Tcl scripts use 0-indexed ports (0, 1). The board diagram uses 1-indexed (Port 1, Port 2).
- **Power sequencing delay.** Power regulators require >1000 ms between disable and re-enable. The state machine enforces this.
- **I2C stall on bad address.** If an invalid device address is issued, the I2C state machine stalls permanently. The only recovery is to reload the bitstream (see [Known Issues](#known-issues--amd-errata)).
- **Page select for upper pages.** Module I2C at `0xA0` uses offset `0x7F` to switch upper pages (e.g., `0x7F=0x00` for lower page, `0x7F=0x03` for page 3 temperatures).

## Near End Loopback

### Architecture

The loopback test uses a single GTF transceiver in near-end PMA loopback mode. TX data is looped back to RX internally at the SerDes level — no external cable or optics needed.

```
JTAG-AXI ──AXI-Lite──► GTFMAC IP (10G) ──TX──┐
                              ▲                │ PMA Loopback
                              └───────RX───────┘
                        HWCHK (frame gen/checker)
                        ILA x3 (status, TX, RX)
```

### Description

The GTF Transceiver Modules can be verified via near-end PMA loopback. The provided Tcl script loads the bitstream, issues JTAG-to-AXI commands to enable loopback mode, generates 50 random packets, and TX/RX data is compared to validate loopback.

### Build & Run

This example uses a prebuilt bitstream — no synthesis required.

```bash
# Fast run (no ILA capture)
vivado -mode batch -source init_gtf.tcl

# Verbose run with ILA waveform capture
vivado -mode batch -source init_gtf_verbose.tcl 2>&1 | tee init_gtf_verbose_out.txt
```

**Required files:** `gtfwizard_0_gtfmac_ex.bit`, `gtfwizard_0_gtfmac_ex.ltx` (both in `tests/loopback_example/`).

### Test Procedure & Results

The Tcl script executes a 30-step sequence: system reset, loopback enable, GTFMAC + HWCHK configuration, block lock acquisition, bitslip alignment, link-up polling, then generates 50 random frames and compares TX/RX counts.

**Pass:** `PASS: TX == RX == 50`

**Fail modes:**
- Zero packets — frame generator did not start (check HWCHK enable, block lock)
- Count mismatch — `FAIL: TX=$tx RX=$rx (expected 50)`

The verbose script also captures ILA waveforms to `ila_captures/` (VCD + CSV) for status, TX, and RX data paths.

### Design Notes

- **RX reset only via AXI.** Asserting TX reset (bit[0]) kills the AXI bus. Only use bit[1] (RX reset). Full system reset is a top-level pin, not AXI-accessible.
- **5-second buffer bypass delay.** There is no AXI register for `gtwiz_buffbypass_rx_done_out`, so the script hard-waits 5 seconds after RX reset before polling link-up.
- **Bitslip timing.** Uses 10 ms polling intervals (not the typical 1 ms) to allow alignment completion.

## Renesas Jitter Cleaner

### Architecture

Two independent I2C paths to the RC38612, plus a frequency counter for verification:

```
                    ┌─────────────────────────┐
                    │       FPGA Fabric        │
                    │                          │
JTAG-AXI ──AXI──►  │  reg_i2c_user_logic ─────┼──► i2c_axi_sequencer ──┐
                    │                          │                        │
            VIO ──► │  BRAM Sequencer ─────────┼──► I2C State Machine ──┤──► RC38612 (0x5B)
                    │                          │                        │
                    │  freq_counter_top ◄──────┼── MGTREFCLK (per bank) │
                    └─────────────────────────┘
```

- **BRAM path:** `.txt` → `txt_to_mem.pl` → `.coe` → BRAM → HW state machine → I2C bulk write
- **User path:** Vivado Tcl → JTAG-AXI → `reg_i2c_user_logic` → `i2c_axi_sequencer` → AXI IIC → I2C single/multi-byte R/W
- **Frequency counter:** Samples jitter cleaner output clocks on each GT bank's MGTREFCLK


The Jitter Cleaner and GTF Banks are hardwired in the following configuration. [datasheet](https://docs.amd.com/r/en-US/ds1016-ul3422/Jitter-Attenuator)
![Jitter Cleaner Architecture](./assets/ul3422/JC.jpg)

### Description

The AMD-provided Renesas I2C programming example operates as a black box: The desired chip configurations are exported from Renesas Timing Commander in a `.txt` format. A Perl script converts the `.txt` register dump into a `.coe` file, which is baked into a BRAM at synthesis time, and a hardware state machine replays the entire sequence over I2C on command. There is no visibility into whether the programming actually succeeded — no readback, no status indication, and no way to interact with individual registers.

To address this, we extended the design with two new capabilities:

**Frequency counter.**
We added a clock frequency measurement module that samples the jitter cleaner's output clocks (routed to each GT bank's MGTREFCLK). This gives immediate feedback on whether the chip is outputting the expected frequencies after programming, and allows us to verify switching between OTP configurations.

**User I2C path.**
We designed and implemented a second I2C controller (`reg_i2c_user_logic.v` + `i2c_axi_sequencer.v`) accessible interactively from the Vivado Tcl console via JTAG-to-AXI. This supports single-byte reads, single-byte writes, and multi-byte burst writes — the latter being critical for the RC38612's paged register architecture, which requires a 4-byte write to offset `0xFC` to select a register page. The Tcl-level interface exposes convenience wrappers (`i2c_pread`, `i2c_pwrite`) that handle page selection automatically.

**Discovering the AMD bug.**
With the user I2C path in hand, we devised a corruption test: write a known bad value to a register, trigger the BRAM programming sequence, then read back the register to check if it was overwritten. The test failed — the BRAM sequencer was not programming correctly. We traced the root cause to AMD's `txt_to_mem.pl` Perl script, which extracts multi-byte data fields in reversed byte order (LSB-first from the hex string). For the page register write, this produces `{0x20 0x10 <page> 0x00}` on the I2C wire instead of the datasheet-specified `{0x00 <page> 0x10 0x20}`, causing every subsequent write to target the wrong register page. The bug wasn't immediately obvious because the provided example programs config 15 — the same configuration the chip loads from OTP at power-up — making the entire BRAM sequence effectively a no-op. The fix is a two-line change in the Perl script to read bytes left-to-right instead of right-to-left.

### Build & Run

**Script execution order:**

```tcl
# 1. Program FPGA and connect debug cores
source Scripts/1_flash_bitstream.tcl

# 2. Trigger BRAM sequencer (VIO reset toggle)
source Scripts/3_enable_renesas_i2c.tcl

# 3. Read jitter cleaner output frequencies
source Scripts/2_read_freq_counters.tcl

# 4. Load interactive I2C procs (i2c_read, i2c_pread, i2c_pwrite, etc.)
source Scripts/4_user_i2c.tcl

# 5. (Optional) Sweep OTP configs via GPIO
source Scripts/5_gpio_config_sweep.tcl
```

**To regenerate the `.coe` from a new Renesas Timing Commander export:**

```bash
perl txt_to_mem.pl <export.txt> > <output.coe>
```

Note: Perl is not installed natively on the lab machines — use Git Bash (see [Prerequisites](#prerequisites--environment-setup)).

### Test Procedure & Results

**Frequency counter verification:**
After programming, run `2_read_freq_counters.tcl` — each bank's MGTREFCLK should report the expected frequency for the active configuration. Switching OTP configs (via `5_gpio_config_sweep.tcl`) should produce different frequency readings.

**BRAM corruption test:**
1. Source `4_user_i2c.tcl`
2. Write a known bad value to a register: `i2c_pwrite 0xB6 <page_offset> <bad_value>`
3. Trigger the BRAM sequencer: `source 3_enable_renesas_i2c.tcl`
4. Read back: `i2c_pread 0xB6 <page_offset>`
5. If the BRAM sequencer works correctly, the register should hold the programmed value, not the bad value

### Design Notes

- **RC38612 page register:** 4-byte burst write to offset `0xFC` with format `{0x00, <page>, 0x10, 0x20}`. The user I2C Tcl wrappers (`i2c_pread`, `i2c_pwrite`) handle this automatically.
- **OTP configs:** GPIO[3:0] selects configs 12–15; pulled high on UL3422 → config 15 at power-up. GPIO pins are defined in XDC but **not connected in RTL** — to switch configs at runtime, drive them as FPGA outputs and toggle `jitt_resetn`.
- **`txt_to_mem.pl` bug:** See the "Discovering the AMD bug" section above. The fix reverses the byte extraction order in the Perl script.

## RECOV_CLK

### Architecture

Two GTF modules share one QSFP-DD port, with the recovered clock routed through the jitter cleaner back to a fabric pin:

```
QSFPDD2 (Port 2) ◄──► MAC GTF (Bank 130)  ── data gen/checker (HWCHK)
                                            └── RXOUTCLK ► BUFG_GT ► ODDRE1 ► RECOV_CLK_65 pin

QSFPDD1 (Port 1) ◄──► RAW GTF (Bank 127)  ── loopback FIFO (requires loopback module)

RC38612 ◄── I2C (Bank 65) ──► MGTREFCLK0 to each GT bank
QSFP power/sideband ◄── I2C (Bank 93) via PCA9546 MUX
freq_counter_top ◄── samples Banks 127–131 + Bank 65 SYNCE inputs
```

### Description

This is the UL3422 port of the UL3524 RECOV_CLK reference design. It demonstrates jitter cleaner programming, data generation/checking on the MAC GTF, loopback on the RAW GTF, clock frequency monitoring, and recovered clock routing to a board pin.

When porting, the following major changes were made:

- **MAC and RAW GTFs** remapped to correct GTF tiles for the UL3422's 2 QSFP-DD ports (vs. UL3524's 4 ports)
- **Single jitter cleaner** and **single I2C MUX reset** (UL3422 has one JC, UL3524 has two)
- **Bank-agnostic RTL** (sync, freq_counter, system, renesas_i2c) carried over verbatim
- **qsfp_i2c subsystem** trimmed from 4 ports to 2
- **state_machine_pwr** replaced with UL3422 version (different power expander bit layout)
- **state_machine_sb** replaced with UL3422 version, with `dbg_plug_state` output re-added for insertion status visibility

### Build & Run

**Requirements:** QSFP-DD loopback module (or cable) on QSFPDD1.

1. Open the Vivado project under `Vivado_Project/`, synthesize, and generate the bitstream
2. Program the device with `clk_recov.bit` and `clk_recov.ltx`
3. In the Vivado Tcl console:

```tcl
cd ./RECOV_CLK/scripts/HwMgr
source ./runme.tcl       ;# Load all helper functions
setup                    ;# Reset, init, and link GTF channels
runme                    ;# Run 5s continuous data transfer (default)
measure_frequency        ;# Read jitter cleaner output clocks
```

**Custom test runs:**
```tcl
setup -n_chan 2                          ;# Initialize 2 channels only
runme -n_chan 2 -n_cycles 3 -n_frames 10 ;# 2 channels, 3 iterations, 10 packets each
runme -n_cycles 5 -delay 60000          ;# 4 channels (default), 5 x 1-minute runs
```

### Test Procedure & Results

**Data integrity test:**
Run `setup` then `runme`. Expected output shows matching FIFO write/read counts and zero error count per channel:

```
Cycle 1 Channel 0, Packets = 78309826, FIFO Wr Count = 587322522, FIFO RD Count = 587322522, FIFO ERR Count = 0
```

**Frequency measurement:**
Run `measure_frequency` after programming the jitter cleaner. Each bank's MGTREFCLK should report the expected frequency for the active OTP config.

### Design Notes

- **Pblock constraints required.** The `BUFG_GT` for the recovered clock can land in the wrong clock region without a pblock pinning it near the GTF. Templates for `pblock_bank_127` and `pblock_bank_130` are in `XDC/constraint.xdc` — fill in GTF tile coordinates after the first synthesis run.
- **AMD documentation errors.** The original RECOV_CLK README and block diagram have the MAC and RAW bank labels **swapped**. XDC comments contain pin function typos (RX vs TX). Always verify against RTL, not docs.
- **Channel count.** `NUM_CHANNEL` in `RTL/clk_recov.v` defaults to 4. Reducing it may generate critical warnings for unused logic — these can be disregarded.

## ILA Ethernet

### Architecture

Same base design as RECOV_CLK, but the RAW GTF's loopback FIFO is replaced with a packet replayer triggered by incoming MAC RX traffic:

```
                        QSFPDD2 ◄──► MAC GTF (Bank 130)
Solarflare NIC ──DAC──► QSFPDD1 ◄──► RAW GTF (Bank 127) ──► Packet Replayer
                                                                    ▲
                                                              MAC RX detect
                                                              triggers TX
```

### Description

This is a modified version of RECOV_CLK where the RAW GTF bank is replaced with an Ethernet packet replayer. When the MAC detects an incoming packet on the RX interface, the replayer is activated and transmits a response packet on the TX interface. This is the only example that does card-to-card Ethernet — used to test packet RX/TX on the QSFP interface against the Solarflare NIC in hft11.

### Build & Run

**Requirements:** Port 1 of UL3422 connected via QSFP-DD to SFP+ DAC cable to Solarflare NIC in hft11.

1. Open the Vivado project under `Vivado_Project/`, synthesize, and generate the bitstream
2. Program the device with the bitstream and `.ltx` file
3. In the Vivado Tcl console:

```tcl
cd ./ila_eth/scripts/HwMgr
source ./runme.tcl       ;# Load helper functions
setup                    ;# Reset and init GTF channels
runme                    ;# Start data transfer
```

ILA cores are included for capturing TX/RX waveforms — configure triggers in Vivado HW Manager as needed.

### Test Procedure & Results

1. Program the board and run `setup` + `runme`
2. Send packets from the Solarflare NIC to the UL3422 (e.g., via raw socket or `ping`)
3. Verify in the ILA capture that the replayer transmits a response for each received packet
4. Check FIFO write/read counts and error counts match (same format as RECOV_CLK output)

### Design Notes

- **Only difference from RECOV_CLK** is the RAW GTF bank's datapath — the rest of the design (jitter cleaner, QSFP I2C, frequency counter, MAC GTF) is identical.
- **Requires external link partner.** Unlike RECOV_CLK (which uses a loopback module), this needs the Solarflare NIC on the other end of the DAC cable.

## Fused PCS + MAC

### Architecture

```
RX path (2 register stages):
  GTF Raw SerDes ──► [Reg] ──► Descramble ──► 64b/66b Decode ──► Frame Extract ──► [Reg] ──► AXI-Stream out
                                                                  (START_4 swap)         ├──► CRC-32 residue check
                                                                                         └──► rx_fcs_valid/ok (1 cycle after tlast)

TX path (1 register stage + GTF TXDATA reg):
  AXI-Stream in ──► Preamble/SFD ──► FCS insert (8x CRC-32) ──► Scramble ──► [Reg] ──► GTF Raw SerDes
                                      DIC-aware IFG management
```

Key modules:
- `ll_eth_mac_pcs.v` — top-level wrapper instantiating `ll_eth_rx` and `ll_eth_tx`
- `ll_eth_rx.v` — fused RX PCS+MAC (descramble, decode, frame extract, CRC check)
- `ll_eth_tx.v` — fused TX MAC+PCS (FCS insert, scramble, encode)
- `ll_eth_cfg.sv` — shared configuration package
- `lfsr_flat.v` — generated by `gen_lfsr_flat.py` (pre-computed XOR equations)
- `hft_filter.v` — Layer 4 UDP port filter (single-cycle Eth/IP/UDP parse, drops non-matching traffic)

### Description

The fused 10GBASE-R PCS+MAC (`ll_eth_mac_pcs`) targets the UL3422's GTF transceivers in raw mode with the elastic buffer bypassed. We eliminate the standard PCS/MAC layer boundary to collapse the datapath into 2 register stages on RX and 2 on TX at 156.25 MHz.

The RX pipeline registers raw SerDes data, then descrambles, decodes the 64b/66b block type (with exceptions of some link handling block types), performs frame extraction with speculative lane-swap buffering for START_4 block support, and emits AXI-Stream output with parallel CRC-32 residue checking. The TX path generates preamble and SFD, scrambles via the matched feedback LFSR, inserts FCS computed from 8 parallel CRC-32 instances spanning all byte alignments, and manages DIC-aware inter-frame gaps. All LFSRs are emitted by a Python generator as explicit pre-computed XOR equations rather than parametric function-based RTL — this approach makes synthesis (Yosys was used for experimentation) resource efficient and fast while producing bit-identical results to the reference (taken from alexforenchich/verilog-ethernet) implementation.

### Build & Run

**Regenerate LFSR equations** (only needed if parameters change):

```bash
python3 rtl/custom/rtl/gen_lfsr_flat.py > rtl/custom/rtl/lfsr_flat.v
```

This generates all LFSR configurations used by `ll_eth_mac_pcs`: 58-bit Fibonacci descrambler/scrambler and CRC-32 (Galois) for data widths 8–64 in steps of 8.

The fused PCS+MAC is integrated into the broader Corundum NIC build flow under `rtl/`. Synthesis targets both Vivado (production) and Yosys (experimentation).

### Test Procedure & Results

- **Bit-identical verification:** Output of `gen_lfsr_flat.py` produces identical scramble/descramble/CRC behavior to the reference `lfsr.v` from alexforenchich/verilog-ethernet.
- **CRC-32 residue check:** `rx_fcs_valid` + `rx_fcs_ok` ports report FCS status 1 cycle after `tlast`, off the data critical path.
- **HFT filter:** Configured with a target UDP destination port (default 5000). Packets not matching are dropped before reaching the host CPU.

### Design Notes

- **Elastic buffer bypass.** The GTF is configured in raw mode with the elastic buffer disabled. This removes the latency of the buffer but requires careful clock domain handling.
- **2-stage pipeline rationale.** RX: one reg for SerDes input, one for decoded output. TX: one pipeline reg, with the GTF's internal TXDATA register serving as the "second" stage. This keeps the datapath as short as possible.
- **CRC off the critical path.** FCS checking runs in parallel with frame output — the result arrives 1 cycle after `tlast` on separate `rx_fcs_valid`/`rx_fcs_ok` ports, so it doesn't add latency to the data path.
- **START_4 support.** Lane-swap handling for START_4 blocks uses a speculative swap buffer (1 mux, 0 extra pipeline stages).
- **Python LFSR generator.** `gen_lfsr_flat.py` pre-computes explicit XOR assign statements for each output bit, replacing the nested-loop Verilog function in the reference design. This produces smaller, faster netlists especially in Yosys.
